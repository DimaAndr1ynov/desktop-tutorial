# DOWNSHOT — лендинг фото/видеооператора (горные лыжи)

Одностраничный статичный сайт продажи услуг фото/видеооператора на горнолыжном склоне.
Владелец: DimaAndr1ynov. Язык сайта: русский.

**Живой сайт:** https://dimaandr1ynov.github.io/desktop-tutorial/

## Структура проекта

- `index.html` — весь сайт (инлайн CSS + JS, дизайн «DOWNSHOT»: тёмная тема, scroll-анимации, светящийся курсор)
- `account.html` + `assets/auth.js` — вход по телефону и личный кабинет клиента (см. раздел ниже)
- `crm.html` + `assets/crm-data.js` — CRM для администратора и сотрудников (см. раздел ниже)
- `assets/hero-ski.jpg` — фон hero-блока (слаломист, 2048×1152)
- `assets/cards/` — фото карточек услуг и портфолио (локальные копии, чтобы не зависеть от Unsplash):
  `stories.jpg`, `school.jpg`, `resort.jpg`, `freeride.jpg`, `events.jpg`, `pf-resort.jpg`
- `photos/` — сюда владелец загружает фото через веб-интерфейс GitHub (Upload files); Claude по запросу привязывает их к сайту
- `.github/workflows/deploy-pages.yml` — деплой на GitHub Pages при пуше в `main` (+ ручной запуск)
- `.github/workflows/fetch-hero-image.yml`, `fetch-card-images.yml` — ручные workflow: скачивают картинки по URL и коммитят в `assets/` (нужны потому, что из среды Claude Code внешние фото-хостинги заблокированы, а у раннеров GitHub доступ есть)

## Блоки сайта (сверху вниз)

1. **Шапка** — логотип-диафрагма, меню, кнопка «Войти»/«Кабинет» (кнопки «Оставить заявку» в шапке нет — убрана по просьбе владельца); прячется при скролле вниз
2. **Hero** — фон `hero-ski.jpg`, текст и кнопки **справа** (выезжают справа), плашка-слоган снизу
3. **Услуги** — 5 карточек 01–05 с фото, при наведении раскрывается описание; номера выровнены в один ряд (`.s-card h3{min-height:38px}`)
4. **Портфолио** — 6 плиток с фото и подписями + анимированный aurora-фон
5. **Тарифы** — «Спуск» 1000 ₽ / «Заезд» 1500 ₽ (выделен) / «Съёмочный день» 3000 ₽
6. **Контакты + футер** — общий aurora-слой (один `.aurora` в `#contact`, продлён на 160px под футер), белая карточка с формой

## Ключевые решения

- Заявки с формы уходят через mailto на **jimmyyobike@onet.pl** (в форме и в подписи «Или сразу на почту»)
- Все фото карточек — локальные, у каждого свой `object-position` (inline style) под положение райдера в кадре; при замене фото это значение надо пересчитывать
- `.aurora` — CSS-версия React-компонента aurora-hero-bg: переливающийся градиент + blur(80px), растянут на `100vw` через `left:50%;transform:translateX(-50%)`, сверху/снизу растворяется в фон, отключается при `prefers-reduced-motion`
- Портфолио заполнено референсными стоковыми кадрами — заменить на работы владельца, когда появятся
- Не использовать `onerror="this.remove()"` на картинках: при временном сбое декодирования плитка теряет фото навсегда

## Личный кабинет клиентов (ТЕСТОВЫЙ режим)

- `account.html` — вход/регистрация по номеру телефона (телефон → 6-значный код → имя + согласие при первом входе) и кабинет: ID клиента, телефон, дата регистрации, имя, «Мои заявки», выход
- `assets/auth.js` — `window.DSAuth`; подключён и в `index.html`: кнопка «Войти» ↔ «Кабинет» в шапке, имя подставляется в форму, к письму заявки добавляются ID и телефон, заявка пишется в историю кабинета
- ID клиента: `DS-XXXXXX` (6 символов без 0/O/1/I), выдаётся при регистрации, при повторном входе тот же
- Сейчас `MODE = 'test'`: SMS не отправляются, вход только по `+79189181188` с кодом `123456`, аккаунты лежат в `localStorage` браузера (ключ `downshot_auth_v1`). Это макет сценария, а не защита — любой может открыть консоль и подменить данные
- Для боевого режима: заменить `provider` в `auth.js` на реальную проверку (Firebase Phone Auth подходит для статического сайта на GitHub Pages; либо SMS-шлюз + свой сервер). ID и данные клиентов тогда должен хранить и выдавать сервер, а не браузер

## CRM для персонала (ТЕСТОВЫЙ режим)

- `crm.html` + `assets/crm-data.js` (`window.DSCRM`, требует `auth.js`). Ссылки на CRM с сайта нет, страница `noindex`
- Вход персонала по телефону + код. Тестовые учётки создаются автоматически (код `123456` для любого): администратор `+79000000001`, оператор `…02`, монтажёр `…03`, менеджер `…04`, кассир `…05`
- Роли и права — `ROLES`/`PERMS` в crm-data.js. Права по умолчанию (администратор может менять галочками в «Сотрудники → Права ролей», хранятся в `data.rolePerms`; права администратора заблокированы):
  - **Администратор** — всё: клиенты (вкл. удаление), сотрудники и права ролей, переписка, файлы (вкл. удаление); себя разжаловать/отключить/удалить нельзя
  - **Менеджер** — клиенты (просмотр, создание, редактирование, без удаления), переписка, загрузка/скачивание файлов
  - **Оператор** — переписка (читать/писать), загрузка/скачивание файлов
  - **Монтажёр** — читать переписку (писать нельзя), загрузка/скачивание файлов
  - **Кассир** — просмотр клиентов (карточка только для чтения), переписка, скачивание файлов (без загрузки)
  - Без права на раздел пункт меню скрыт; без `clients.edit` карточка клиента только для чтения; без `messages.send` вместо поля ввода плашка «Только чтение»
  - Миграция данных v2 (`migrate()`): старая роль «Сотрудник» (`employee`) → «Оператор», досоздаются тестовые учётки новых ролей
- Переписка оформлена как в Telegram (и в CRM, и в кабинете клиента): пузыри с «хвостиком» у последнего в серии (серия = одна сторона, интервал <5 мин), время и галочка внутри пузыря (1 галочка = тест, не отправлено), разделители дат, фон-обои, аватары с инициалами. Поле ввода растёт до 140px без полосы прокрутки; Enter — отправить, Shift+Enter — перенос (на тачскринах Enter = перенос). Скрепка отправляет файл сообщением (`DSCRM.sendFile`) — он же попадает в «Файлы» клиента
- Граница между списком клиентов и перепиской перетаскивается: 200–560px — полный список, до упора влево (76px) — режим «только аватары» (`.dlg.compact`: имя в подсказке, непрочитанное — точкой на аватаре); промежуточная ширина при отпускании прилипает к ближайшему варианту (порог 138px). Переписке остаётся ≥360px, ширина хранится в `localStorage` (`downshot_crm_list_w`); двойной клик — сброс к 300px, стрелки ←/→ (Shift — шаг крупнее). На ≤860px граница скрыта: список и чат там на отдельных экранах
- Сообщения и файлы видны клиенту в `account.html` («Сообщения от студии» с ответом, «Файлы от студии» со скачиванием); ответ клиента в CRM отмечается точкой и счётчиком у «Диалогов». Вкладки синхронизируются через событие `storage`
- Хранение в тесте: `localStorage` (`downshot_crm_v1` — персонал, сессия, сообщения, метаданные файлов; клиенты — в `downshot_auth_v1`), содержимое файлов — IndexedDB `downshot_files`, лимит 25 МБ на файл. Всё живёт в одном браузере: админ и сотрудник на разных устройствах друг друга не увидят
- Права проверяются в браузере — это макет, не защита. Для боевого режима нужен сервер: база (клиенты, персонал, переписка), хранилище файлов, SMS-шлюз для отправки и приёма ответов, проверка ролей на сервере

## Адаптивность (все экраны 320px – 2560px+)

- Размеры «резиновые»: шрифты, отступы и высоты заданы через `clamp(мин, формула с vw, макс)` — новые размеры писать так же, а не фиксированными px
- Ширина контента — `--wrap` (1180px → до 1760px на 2K/4K), поля — `--gutter`; `--pad-l/--pad-r` учитывают вырез экрана iPhone (`viewport-fit=cover` + `env(safe-area-inset-*)`)
- Раскладки по ширине:
  - ≥1100px с мышью — 5 карточек услуг в ряд, описание по наведению
  - 861–1099px **и любой тачскрин шире 860px** (`hover:none`) — услуги сеткой 3+2, описание видно сразу
  - ≤760px — тарифы в одну колонку (макс. 500px по центру), шире — три в ряд
  - портфолио: плитки 4:3, на экранах <600px — квадратные
  - ≤860px — мобильная раскладка; 561–860px — услуги в 2 колонки, 600–860px — портфолио в 3 колонки
  - ≤380px — мелкие телефоны (iPhone SE и т.п.)
  - высота ≤520px в landscape — телефон боком: заголовок hero в одну строку, первый экран помещается целиком
- Полоса прокрутки страницы скрыта по просьбе владельца (`scrollbar-width:none` + `::-webkit-scrollbar`), прокрутка работает
- На тачскринах поля формы 16px (иначе iOS зумит страницу при фокусе)
- Проверка: нет горизонтальной прокрутки (`document.documentElement.scrollWidth === innerWidth`) на 320, 390, 667×375, 844×390, 768, 1024, 1366, 1920, 2560

## Рабочий процесс (важно)

- Ветка разработки: `claude/photo-video-operator-site-fijp9n`; перед новой правкой пересоздавать её от `origin/main` (`git checkout -B <ветка> origin/main`), т.к. PR мержатся squash'ем
- Публикация: PR → squash-merge в `main` → деплой Pages запускается автоматически
- НО: коммиты, сделанные workflow-ботом (fetch-*-image), деплой НЕ триггерят — после них запускать `deploy-pages.yml` вручную (workflow_dispatch)
- Репозиторий публичный (это требование бесплатного GitHub Pages)
- Проверка вёрстки: Playwright + Chromium `/opt/pw-browsers/chromium`, скриншоты; scroll-анимации на fullPage-скриншоте включать принудительно:
  `document.querySelectorAll('.reveal-group').forEach(g => g.classList.add('in-view'))`
- Известный артефакт песочницы: в headless-скриншотах часть картинок случайно не растеризуется, хотя в DOM `complete=true` и `naturalWidth>0`. Проверять факт загрузки через DOM, а не только глазами по скриншоту
