# DOWNSHOT — лендинг фото/видеооператора (горные лыжи)

Одностраничный статичный сайт продажи услуг фото/видеооператора на горнолыжном склоне.
Владелец: DimaAndr1ynov. Язык сайта: русский.

**Живой сайт:** https://dimaandr1ynov.github.io/desktop-tutorial/

## Структура проекта

- `index.html` — весь сайт (инлайн CSS + JS, дизайн «DOWNSHOT»: тёмная тема, scroll-анимации, светящийся курсор)
- `account.html` + `assets/auth.js` — вход по телефону и личный кабинет клиента (см. раздел ниже)
- `crm.html` + `assets/crm-data.js` — CRM для администратора и сотрудников (см. раздел ниже)
- `assets/hero-ski.jpg` — фон hero-блока (слаломист, 2048×1152)
- `assets/cards/` — фото карточек услуг и портфолио (локальные копии, чтобы не зависеть от Unsplash):
  `stories.jpg`, `school.jpg`, `resort.jpg`, `freeride.jpg`, `events.jpg`, `pf-resort.jpg`
- `photos/` — сюда владелец загружает фото через веб-интерфейс GitHub (Upload files); Claude по запросу привязывает их к сайту
- `.github/workflows/deploy-pages.yml` — деплой на GitHub Pages при пуше в `main` (+ ручной запуск)
- `.github/workflows/fetch-hero-image.yml`, `fetch-card-images.yml` — ручные workflow: скачивают картинки по URL и коммитят в `assets/` (нужны потому, что из среды Claude Code внешние фото-хостинги заблокированы, а у раннеров GitHub доступ есть)

## Блоки сайта (сверху вниз)

1. **Шапка** — логотип-диафрагма, меню, кнопка «Войти»/«Кабинет» (кнопки «Оставить заявку» в шапке нет — убрана по просьбе владельца); прячется при скролле вниз
2. **Hero** — фон `hero-ski.jpg`, текст и кнопки **справа** (выезжают справа), плашка-слоган снизу
3. **Услуги** — 5 карточек 01–05 с фото, при наведении раскрывается описание; номера выровнены в один ряд (`.s-card h3{min-height:38px}`)
4. **Портфолио** — 6 плиток с фото и подписями + анимированный aurora-фон
5. **Тарифы** — «Спуск» 1000 ₽ / «Заезд» 1500 ₽ (выделен) / «Съёмочный день» 3000 ₽
6. **Контакты + футер** — общий aurora-слой (один `.aurora` в `#contact`, продлён на 160px под футер), белая карточка с формой

## Ключевые решения

- Заявки с формы уходят через mailto на **jimmyyobike@onet.pl** (в форме и в подписи «Или сразу на почту»)
- Все фото карточек — локальные, у каждого свой `object-position` (inline style) под положение райдера в кадре; при замене фото это значение надо пересчитывать
- `.aurora` — CSS-версия React-компонента aurora-hero-bg: переливающийся градиент + blur(80px), растянут на `100vw` через `left:50%;transform:translateX(-50%)`, сверху/снизу растворяется в фон, отключается при `prefers-reduced-motion`
- Портфолио заполнено референсными стоковыми кадрами — заменить на работы владельца, когда появятся
- **SEO** (`index.html`, `<head>`): meta description, canonical, Open Graph (картинка — `assets/hero-ski.jpg`), JSON-LD `ProfessionalService` с тарифами. Цены в JSON-LD должны совпадать с блоком «Тарифы» — при смене цен менять в обоих местах. `sitemap.xml` и `robots.txt` лежат в корне проекта; Google/Яндекс читают robots только с корня домена `github.io`, поэтому карту сайта надо добавить вручную в Search Console / Яндекс Вебмастер. `account.html` и `crm.html` закрыты `noindex`
- Не использовать `onerror="this.remove()"` на картинках: при временном сбое декодирования плитка теряет фото навсегда

## Личный кабинет клиентов (ТЕСТОВЫЙ режим)

- `account.html` — вход/регистрация по номеру телефона (телефон → 6-значный код → имя + согласие при первом входе) и кабинет: ID клиента, телефон, дата регистрации, имя, «Мои заявки», выход
- Кабинет в две колонки (`.cab-layout`): слева липкая колонка профиля `.profile` сверху вниз — аватар с инициалами (цвет по ID, как в CRM) и рядом имя («Без имени», если не задано), ID с кнопкой «Копировать», номер телефона, кнопка «Оставить заявку», ниже меню разделов `#cabMenu`: «Сообщения», «Файлы от студии» (счётчик), «Мои заявки» (счётчик), «Настройки», и самой последней — «Выйти» (`#logout`, под «Настройками»). Меню переключает правую часть (`.panel[data-panel]`, `showView()`); раздел отражается в хеше (`account.html#files`, `#requests`, `#settings`, сообщения — без хеша). Меню сделано `div role=navigation`, не `<nav>`: на `nav` в этом файле висят стили шапки. **Режим приложения** на телефоне и планшете (CSS-условие `(max-width:860px), (pointer:coarse) and (max-width:1366px)`, то же в скрипте как `APP_MQ`; на компьютере всё как раньше): сайтовая шапка скрыта (`body.in-cabinet`), вместо неё шапка-приложение `.appbar` (кнопка ☰, заголовок раздела, плашка ТЕСТ, аватар), левая колонка `.profile` стала **панелью, выезжающей слева** (кнопка ☰ или аватар, свайп от левого края, закрытие по ×, затемнению или Esc; внутри профиль, «Оставить заявку», меню разделов, «Выйти», «На сайт», пометка про тестовый режим). Основа экрана — «Сообщения» (чат на всю высоту, без рамки) и «Файлы», они же в нижней панели вкладок `.tabbar` (на файлах счётчик); «Мои заявки» и «Настройки» открываются из выезжающей панели. При открытой клавиатуре (`body.kb`) вкладки прячутся. Панель и вкладки сделаны не на `<nav>`: на этот тег в файле висят стили шапки сайта
- «Настройки» (раздел справа, `#setPanel`): редактируются имя и e-mail для связи (`DSAuth.updateUser({name, email})`, e-mail проверяется, пустой допустим); телефон и дата регистрации показываются только для чтения. Телефон — логин, его смена по коду пока не сделана. E-mail подставляется в форму заявки на главной вместе с именем
- **Демо-режим кабинета** (только `MODE='test'`; плашка над разделами, кнопка «Включить/Выключить демо-режим»; `DSCRM.seedCabinetDemo(id)` / `clearCabinetDemo(id)` / `hasCabinetDemo(id)`, в crm-data.js, без прав сотрудника — клиент меняет только свой аккаунт): добавляет текущему клиенту переписку со студией (9 сообщений, ответы клиента, сообщения-файлы), 4 файла для скачивания (3 сгенерированных JPG-кадра и txt, содержимое в IndexedDB) и 2 заявки. Всё помечено `demo:true` и удаляется одним кликом, остальные данные не трогаются
- `assets/auth.js` — `window.DSAuth`; подключён и в `index.html`: кнопка «Войти» ↔ «Кабинет» в шапке, имя подставляется в форму, к письму заявки добавляются ID и телефон, заявка пишется в историю кабинета
- ID клиента: `DS-XXXXXX` (6 символов без 0/O/1/I), выдаётся при регистрации, при повторном входе тот же
- Сейчас `MODE = 'test'`: SMS не отправляются, вход только по `+79189181188` с кодом `123456`, аккаунты лежат в `localStorage` браузера (ключ `downshot_auth_v1`). Это макет сценария, а не защита — любой может открыть консоль и подменить данные
- Для боевого режима: заменить `provider` в `auth.js` на реальную проверку (Firebase Phone Auth подходит для статического сайта на GitHub Pages; либо SMS-шлюз + свой сервер). ID и данные клиентов тогда должен хранить и выдавать сервер, а не браузер

## CRM для персонала (ТЕСТОВЫЙ режим)

- `crm.html` + `assets/crm-data.js` (`window.DSCRM`, требует `auth.js`). Ссылки на CRM с сайта нет, страница `noindex`
- **Светлая тема**: CRM светлая (в отличие от тёмных сайта и кабинета). Цвета — переменные `:root` в начале `<style>` (`--bg`, `--surface`, `--text` и др.), поверх них блок «светлая тема» в конце `<style>` переопределяет переменные и жёстко заданные цвета (роли, плашки, пузыри чата, оверлей). Новые цвета писать через переменные
- Вход персонала по телефону + код. Тестовые учётки создаются автоматически (код `123456` для любого): администратор `+79000000001`, оператор `…02`, монтажёр `…03`, менеджер `…04`, кассир `…05`
- Роли и права — `ROLES`/`PERMS` в crm-data.js. Права по умолчанию (администратор может менять галочками в «Сотрудники → Права ролей», хранятся в `data.rolePerms`; права администратора заблокированы):
  - **Администратор** — всё: клиенты (вкл. удаление), сотрудники и права ролей, переписка, файлы (вкл. удаление); себя разжаловать/отключить/удалить нельзя
  - **Менеджер** — дашборд, клиенты (просмотр, создание, редактирование, без удаления), оплаты (просмотр и внесение), переписка, загрузка/скачивание файлов
  - **Оператор** — переписка (читать/писать), загрузка/скачивание файлов
  - **Монтажёр** — читать переписку (писать нельзя), загрузка/скачивание файлов
  - **Кассир** — просмотр клиентов (карточка только для чтения), оплаты (просмотр и внесение), переписка, скачивание файлов (без загрузки); дашборда нет
  - Без права на раздел пункт меню скрыт; без `clients.edit` карточка клиента только для чтения; без `messages.send` вместо поля ввода плашка «Только чтение»
  - Миграция данных v2 (`migrate()`): старая роль «Сотрудник» (`employee`) → «Оператор», досоздаются тестовые учётки новых ролей
  - Миграция v3: права `dashboard.view`, `payments.view`, `payments.edit`; если администратор уже менял права роли, новые права по умолчанию дописываются в её список, иначе роль осталась бы без них
- Переписка оформлена как в Telegram (и в CRM, и в кабинете клиента): пузыри с «хвостиком» у последнего в серии (серия = одна сторона, интервал <5 мин), время и галочка внутри пузыря (1 галочка = тест, не отправлено), разделители дат, фон-обои, аватары с инициалами. Поле ввода растёт до 140px без полосы прокрутки; Enter — отправить, Shift+Enter — перенос (на тачскринах Enter = перенос). Скрепка отправляет файл сообщением (`DSCRM.sendFile`) — он же попадает в «Файлы» клиента
- **Оплаты** (`data.payments` в `downshot_crm_v1`): блок «Оплаты» внизу карточки клиента — тариф (Спуск 1000 / Заезд 1500 / Съёмочный день 3000 / Другое; выбор подставляет сумму), сумма, способ (карта / наличные / перевод), комментарий. Вносит тот, у кого `payments.edit`, удаляет только `clients.delete` (админ). В таблице клиентов столбец «Оплачено». Это единственный источник выручки
- **Дашборд** (раздел «Аналитика» (прежнее «Дашборд»), первый в меню, право `dashboard.view`; `DSCRM.stats(period)`, `renderDashboard()` в crm.html): период 7 / 30 / 90 дней или всё время (хранится в `downshot_crm_period`); карточки — клиенты, заявки с сайта, выручка (с динамикой к прошлому периоду), средний чек и конверсия в оплату; графики — выручка по дням / неделям / месяцам (SVG, на узком экране прокручивается внутри рамки), клиенты по статусам, выручка по тарифам и способам оплаты; списки — «Требуют внимания» (ждут ответа, новые без ответственного, съёмка без оплаты), нагрузка на сотрудников, последние события. Клик по клиенту открывает карточку или диалог
- **Демо-данные** (только тестовый режим, кнопка в верхней плашке дашборда; `DSCRM.seedDemo()` / `clearDemo()`): 9 вымышленных клиентов (телефоны `+7900100000x`, флаг `demo:true`) с заявками, оплатами за последние 4 недели и двумя непрочитанными сообщениями. Удаляются одним кликом, настоящие данные не затрагиваются. На живом сайте CRM пустая, пока не нажать кнопку
- **Меню CRM**: сверху «Аналитика», «Проекты», «Диалоги»; ниже группа «Операции»: «Клиенты», «Аренды», «Флот», «Ремонты», «Склад», «Передачи», «Услуги мастера», «Сотрудники». Заголовок группы виден, если доступен хотя бы один её пункт
- **Операции** (группа «Операции» в меню, шесть разделов; адаптация меню системы проката под оборудование студии; телеметрии и устройств нет): «Аренды» (техника клиентам: клиент, срок, сумма, кнопка «Вернуть», просрочка по дате возврата), «Флот» (камеры, дроны, экшн-камеры, стабилизаторы: статусы В наличии / В аренде / У сотрудника / В ремонте / Списано, меняются сами), «Ремонты» (принят → в работе → готов → выдан, при «выдан» техника возвращается во флот), «Склад» (расходники, остаток, минимум, метка «Мало» при остатке ≤ минимума, кнопки −1/+1), «Передачи» (выдача техники сотруднику и приём обратно), «Услуги мастера» (чистка, калибровка, прошивки: запланирована → выполнена). Данные `data.ops = {rentals, fleet, repairs, stock, transfers, services}` в `downshot_crm_v1`, API `DSCRM.opsList/opsSave/opsAction/opsDelete/opsRefs` в crm-data.js (побочные эффекты на статус техники делает слой данных: занятую технику нельзя выдать или сдать в аренду), UI — один общий рендер `renderOps()` / `openOps()` с описанием разделов в `opsDef()` в crm.html. Права `ops.view` (менеджер, оператор, монтажёр, админ) и `ops.edit` (менеджер, оператор, админ), кассиру раздел скрыт; миграция v6 дописывает права в уже изменённые списки. **Демо-режим операций** (плашка в каждом разделе, `seedDemoOps()` / `clearDemoOps()`, флаг `demo:true`): 8 единиц техники, 4 аренды (одна просрочена), 3 передачи, 3 ремонта, 6 позиций склада (две «Мало»), 4 услуги. На телефоне меню CRM — горизонтальная прокручиваемая полоса иконок
- **Сотрудники** (раздел «Сотрудники», `staff.edit`; `DSCRM.staffOverview()`, `renderStaff()`): таблицы по **группам = ролям** (Администрация, Менеджеры, Операторы, Монтажёры, Кассиры) с заголовком группы (на смене X из Y, часы, оклады). В строке: имя и телефон, **статус смены** (выпадающий список прямо в таблице), часы за сегодня, часы за месяц с полоской выполнения нормы (160 ч, `NORM_HOURS`), **оклад**, доступ. Сверху четыре карточки: на смене сейчас (с разбивкой по статусам), отработано сегодня, за месяц, оклады. Карточка сотрудника: имя, телефон, группа, оклад (подсказка «ставка ≈ N ₽ в час»), статус, доступ
- **Статусы смены** (`STAFF_STATUSES`): В работе, На съёмке, Перерыв (эти три **считаются** в отработанные часы), На обеде, Не на смене, В отпуске, На больничном (не считаются). Журнал смен — `staff.log = [{s, t}]` в `downshot_crm_v1`, часы — сумма интервалов (`hoursOf()`). Вход в CRM ставит «В работе» (если был «Не на смене»), выход — «Не на смене». «Мой статус» (`#shiftBar`) над содержимым есть у каждого сотрудника, чужой статус меняет только `staff.edit`. Закрыть вкладку без выхода смену не завершает, статус придётся поправить вручную. На дашборде панель «Команда сейчас» (`DSCRM.team()`, без окладов, видна тем, у кого `dashboard.view`)
- Миграция v4: общие имена тестовых учёток заменены на человеческие (Андрей Волков, Ирина Соколова, Максим Орлов, Елена Миронова, Наталья Крылова), добавлены оклады по умолчанию и журнал смен. **Демо-сотрудники** (кнопка в «Сотрудниках», `seedDemoStaff()`/`clearDemoStaff()`, флаг `demo:true`, телефоны `+7900200000x`): 8 человек с окладами, разными статусами и часами за месяц, удаляются одним кликом
- **Карточка сотрудника** (клик по строке в «Сотрудниках», `staffDetail()`, `openStaff()`): у **всех** групп — «Расчёт зарплаты» (оклад за норму 160 ч, ставка в час = оклад / 160, отработано часов, до нормы осталось или сверх нормы, **начислено = ставка × отработанные часы**, сверх нормы по той же ставке), «Отработанные часы» (сегодня, месяц, % нормы, столбики по дням месяца) и форма данных. У **операторов и монтажёров** (роли с правом `projects.work`, администратор в их число не входит) добавляются «Проекты» (карточки с действиями), «Завершено в этом месяце», «Передано другим» и «Проделанная работа» (по каждому проекту: часы сотрудника за месяц, статус, что сделано). У менеджеров, кассиров и администратора только часы и зарплата
- **Проекты** (`data.projects`, раздел «Проекты» в меню, `projects.any` = есть `projects.work` или `projects.manage`): название, тип (Съёмка / Монтаж / Другое), клиент, исполнитель, дедлайн, описание. Статус: Не начат → **Начать** → В работе ↔ **Пауза** (Продолжить) → **Завершить** (форма «Что сделано», результат хранится в проекте) или **Передать** другому оператору/монтажёру (передача закрывает идущий отрезок времени, проект у нового исполнителя встаёт на паузу или «не начат», у прежнего остаётся в «Передано» с его временем). Время считается по отрезкам `sessions: [{staffId, from, to}]`, идёт «● идёт»; у исполнителя одновременно один проект в работе, остальные ставятся на паузу автоматически. Дедлайн подсвечивается: просрочен, сегодня/завтра, через N дн.
- Права проектов: `projects.work` (оператор, монтажёр: видят и ведут только свои, передают коллегам-исполнителям) и `projects.manage` (менеджер и администратор: видят все, создают, меняют, назначают, удаляют; действия за любого исполнителя). Миграция v5 дописывает эти права в уже изменённые списки ролей. **Демо-режим проектов** (плашка вверху раздела «Проекты», только тестовый режим и только тем, у кого `projects.manage`; `DSCRM.seedDemoProjectsOnly()` / `clearDemoProjects()`): кнопка «Включить демо-режим» добавляет 10 проектов (`demo:true`) в разных состояниях — в работе, на паузе, не начат, завершён с результатом, просрочен, передан коллеге; исполнители берутся из **уже существующих** операторов и монтажёров (с двумя тестовыми учётками проекты делятся между ними и передач нет, с демо-сотрудниками появляются и передачи), если исполнителей нет, а право `staff.edit` есть, создаются демо-сотрудники. «Выключить демо-режим» удаляет только демо-проекты. Демо-сотрудники тоже создают демо-проекты, если их ещё нет (дублей нет), а при удалении демо-сотрудников демо-проекты удаляются тоже
- Граница между списком клиентов и перепиской перетаскивается: 200–560px — полный список, до упора влево (76px) — режим «только аватары» (`.dlg.compact`: имя в подсказке, непрочитанное — точкой на аватаре); промежуточная ширина при отпускании прилипает к ближайшему варианту (порог 138px). Переписке остаётся ≥360px, ширина хранится в `localStorage` (`downshot_crm_list_w`); двойной клик — сброс к 300px, стрелки ←/→ (Shift — шаг крупнее). На ≤860px граница скрыта: список и чат там на отдельных экранах
- Сообщения и файлы видны клиенту в `account.html` («Сообщения от студии» с ответом, «Файлы от студии» со скачиванием); ответ клиента в CRM отмечается точкой и счётчиком у «Диалогов». Вкладки синхронизируются через событие `storage`
- Хранение в тесте: `localStorage` (`downshot_crm_v1` — персонал, сессия, сообщения, метаданные файлов; клиенты — в `downshot_auth_v1`), содержимое файлов — IndexedDB `downshot_files`, лимит 25 МБ на файл. Всё живёт в одном браузере: админ и сотрудник на разных устройствах друг друга не увидят
- Права проверяются в браузере — это макет, не защита. Для боевого режима нужен сервер: база (клиенты, персонал, переписка), хранилище файлов, SMS-шлюз для отправки и приёма ответов, проверка ролей на сервере

## Адаптивность (все экраны 320px – 2560px+)

- Размеры «резиновые»: шрифты, отступы и высоты заданы через `clamp(мин, формула с vw, макс)` — новые размеры писать так же, а не фиксированными px
- Ширина контента — `--wrap` (1180px → до 1760px на 2K/4K), поля — `--gutter`; `--pad-l/--pad-r` учитывают вырез экрана iPhone (`viewport-fit=cover` + `env(safe-area-inset-*)`)
- Раскладки по ширине:
  - ≥1100px с мышью — 5 карточек услуг в ряд, описание по наведению
  - 861–1099px **и любой тачскрин шире 860px** (`hover:none`) — услуги сеткой 3+2, описание видно сразу
  - ≤760px — тарифы в одну колонку (макс. 500px по центру), шире — три в ряд
  - портфолио: плитки 4:3, на экранах <600px — квадратные
  - ≤860px — мобильная раскладка; 561–860px — услуги в 2 колонки, 600–860px — портфолио в 3 колонки
  - ≤380px — мелкие телефоны (iPhone SE и т.п.)
  - высота ≤520px в landscape — телефон боком: заголовок hero в одну строку, первый экран помещается целиком
- Полоса прокрутки страницы скрыта по просьбе владельца (`scrollbar-width:none` + `::-webkit-scrollbar`), прокрутка работает
- На тачскринах поля формы 16px (иначе iOS зумит страницу при фокусе)
- Проверка: нет горизонтальной прокрутки (`document.documentElement.scrollWidth === innerWidth`) на 320, 390, 667×375, 844×390, 768, 1024, 1366, 1920, 2560

## Рабочий процесс (важно)

- Ветка разработки: `claude/photo-video-operator-site-fijp9n`; перед новой правкой пересоздавать её от `origin/main` (`git checkout -B <ветка> origin/main`), т.к. PR мержатся squash'ем
